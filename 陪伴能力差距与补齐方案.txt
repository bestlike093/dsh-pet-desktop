============================================================
0. 三句话结论
============================================================
第一，功能数量不是主要差距。四个插件加起来的配置有几百项，照着补会把桌宠做成控制台。

第二，真正的差距在"三件事互相知道"：她记着什么、她此刻什么状态、她为什么现在开口。
       这四个插件最强的地方是三方联动：
       开口前读记忆与身体，说完写回记忆，日程作为由头。
       我们现在是三个独立模块，各管各的。

第三，有一个必须先纠正的认知问题：Live2D 运行时实际没有启用。
       README 写着 PixiJS + pixi-live2d-display，REQUIREMENTS 写着"仅取首帧"，
       而 live2dAdapter.ts 的开头注释写得很清楚（见 1.3）。
       这直接影响"立绘"这条产品线怎么讲、怎么排期。

============================================================
1. 现状盘点（先确认我们有什么）
============================================================
1.1 已经达成的（README 自述，16 项）
  五类形象适配器、降级不白屏、动作三层通道、自动描边、
  状态栏三档、语音（本地 TTS / 免打扰 / 字数 / 间隔）、
  桌面聊天窗 + 加密落盘 + 人格提示词、
  记忆（加密、可视化、条数上限、摘要压缩、按话题挑片段）、
  主动说话（时间/天气/陪伴/心情/记忆生成、话头账本）、
  素材包、设置页与三步引导、能力中心（猜拳/战绩）、
  模块系统、余额监控、QQ 远程拍板、本机同步。

1.2 项目自己承认还没做的（REQUIREMENTS 3.1 / 3.2）
  记忆衰减：packages/memory 有 decay()，桌面壳仍是纯 FIFO
  聊天历史与记忆分层：两者共用一套存取
  语音双轨：无云端兜底、无手动导入音色
  多 provider：只支持 DeepSeek，端点不可切换
  QQ 唤醒与历史：只有 webhook 拍板
  B 站通道：有浏览能力，桌面壳未接线
  Cyrene 分层记忆：未接
  模块沙箱接管桌面功能：未做

1.3 三处文档与实现不一致（会误导排期，必须先修）
  (a) Live2D
      README：PixiJS + pixi-live2d-display，动作三层 native / param / pixi
      REQUIREMENTS：仅取首帧纹理显示，未接运行时
      live2dAdapter.ts 第 1-9 行：
        「【保留 · 前期不实现 · 依赖 E4/E8】
          Live2D 在 2D 首发阶段只保留端口，不启用渲染路径。
          E4（真机加载）/ E8 到位前，本文件的所有结论都基于模拟纹理，
          真实模型加载从未发生。」
      结论：当前 Live2D 不可用。README 需要改，设置页需要明说
            "当前为静态预览/降级显示"，不能让人以为导入就能动。

  (b) 设置页数量
      README：九组设置页
      实际：7 组 17 个面板（上一份文档已逐项列出）

  (c) 游戏日常
      REQUIREMENTS 第 4 节明确写「不做游戏日常自动化（接 BetterGI 等）」
      设置页却有完整的"游戏日常 / 游戏助手"，还带两次风险确认和手输短语。
      要么删入口，要么改需求文档，不能两边同时成立。

  (d) 主动说话的"话头账本"
      README 说"话头有账本，提过不重复"
      设置页只有 5 项，用户看不到账本、也看不到"为什么这次开口"。
      后端有能力，前端没入口，等于没有。

1.4 已经被验证存在的能力（比文档写的多）
  companion.ts 显示：日程已经支持
    - 读取今天这份节目单（agendaNote）
    - 手动顺延，上限 240 分钟，睡觉不动（interruptAgenda）
  也就是说"日程被打断后顺延"这件事有后端，缺的是用户能看见、能操作的入口，
  以及"被打断的旧事挂起后回去接着做"。

============================================================
2. 四个插件真正的机制（只提炼能迁移的）
============================================================
memory_companion：分槽 + 召回 + 来源 + 可见性
  记忆按身份 / 偏好 / 事件 / 关系分槽；
  按当前话题召回，不是按时间倒序全塞；
  每条能说清从哪来；
  不同场景（私聊/群聊）可见范围不同。

private_companion：把能力收成一条路径
  八步引导 + 工作区分组，让第一次使用的人不用理解模块；
  它的价值在产品化，不在功能数量。

autonomous_social：四段式
  念头：管"等多久"（activity_level、urge_refill_hours）
  由头：管"为什么说"（刚做完的事、你提过没下文的、到点的问候）
  闸门：管"能不能说"（安静时段、冷却、频率、关系档、模型否决）
  记账：管"说过什么、结果如何"（发送记录、防重复、沉默放弃）
  关键判据：派不出由头就不说。这一条决定了它像人，不像定时器。

humanoid_core：状态按时间走，不按消息走
  身体轴（精力/困意/睡眠债/饥饿/社交能量）按时间积分，停机后补算；
  日程按 15 分钟决策窗现排，可打断、可挂起、可续做；
  情绪是状态机，有基线、有衰减、有冷静期、有道歉回温；
  给模型的是体感（"有点困"），给用户的是数值面板。

============================================================
3. 差距矩阵
============================================================
等级说明：★=缺了会被用户感知；☆=缺了体验不完整；○=可以不做

3.1 记忆层（对标 memory_companion）
  [★] 分槽
      插件：身份/偏好/事件/关系四槽，各槽召回策略不同
      我们：一条记忆流 + 摘要压缩
      补法：memory 条目加 slot 字段，写入时按规则归类；
            设置页只显示四组，不暴露规则
  [★] 重要度与衰减
      插件：按重要度保留，久不用降权
      我们：纯 FIFO（REQUIREMENTS 自述）
      补法：把已有的 decay() 接进桌面壳，评分 = 提及次数 + 时间衰减 + 用户固定
  [★] 来源可追溯
      插件：每条能回到原对话
      我们：可视化有，来源没有
      补法：条目加 sourceMessageId / sourceTime，详情里显示"这句话来自 11 月 3 日的聊天"
  [☆] 可编辑 / 可固定
      插件：可改、可锁
      我们：只能逐条删除
      补法：加"固定"和"编辑"；固定项不参与衰减
  [☆] 说完写回
      插件：主动开口后把结果写回记忆
      我们：主动台词不写回
      补法：主动消息发出后，写一条事件槽（说了什么、对方有无回应）
  [☆] 召回方式
      插件：embedding 语义检索
      我们：按当前话题挑片段（未验证是否语义）
      补法：单人桌宠先用"关键词 + 摘要"够用，别急着上 embedding 成本
  [○] 可见性/权限拓扑
      插件：多用户、私聊/群聊可见性
      我们：单人桌宠，不需要

3.2 主动层（对标 autonomous_social）
  [★] 由头
      插件：先说清"为什么是现在"，派不出就不说
      我们：时间/天气/陪伴/心情/记忆直接生成一句
      差距：现在更接近"定时播报"，不是"她想起一件事"
      补法：最小三由头——
            ① 未完话题（你说过"明天要面试"，到点问结果）
            ② 日程节点（她刚做完一件事，想跟你说）
            ③ 隔久了问候（按距上次说话多久，不绑日历）
  [★] 安静时段
      插件：23:00–07:00，整轮不发，手动触发也拦
      我们：设置页没有
      补法：全局安静时段 + 起床后补一次评估
  [★] 每日上限与冷却
      插件：每人每天上限、两次之间最小间隔、每小时安全闸
      我们：只有"开口间隔 1–120 分钟"，默认 12
      补法：最小间隔 + 每日上限 + 连续未回复降频
  [★] 沉默放弃
      插件：连续 3 天没回应就全面停发，等对方先开口
      我们：没有
      补法：3 天无回应 → 停主动，界面上写"她暂时不主动找你了"
  [☆] 发送前否决（LLM gate）
      插件：模型可以先说 NO
      我们：只有失败回退本地短句
      补法：生成后加一道"该不该说"的判定，拒绝就留到下一轮
  [☆] 未完成话题 / 追问 / 接话 / 收场
      插件：四类行为各有时间窗
      我们：没有
      补法：先做"未完话题"和"收场"，追问与接话后置
  [☆] 关系分档
      插件：越熟越自然，越生越克制
      我们：无熟悉度概念
      补法：单人桌宠简化为"认识天数 + 互动轮次"一个数，
            只影响频率与称呼，不做排行榜
  [☆] 说话习惯画像
      插件：从真实聊天统计句长、口头禅、emoji
      我们：人格提示词静态
      补法：统计最近 200 条的平均句长与高频词，注入提示词；
            设置页给一个"像不像她"的开关
  [○] 跨用户去重 / 群聊心流 / 破冰 / 多 bot
      单人桌宠不需要
  [○] 正在输入
      桌面场景无意义，可换成气泡打字机效果

3.3 身体与生活层（对标 humanoid_core）
  [★] 连续状态
      插件：精力、困意、睡眠债、饥饿、社交能量，按时间积分
      我们：有"情绪与反思"页，但没有连续状态机
      补法：最小三值——精力 / 心情 / 今天陪了多久；
            关机后按离线时长补算，上限 72 小时
  [★] 状态影响开口
      插件：精力低就少开口，社交能量低就几乎不动
      我们：主动只看间隔
      补法：精力 < 阈值时不主动，或只发一句很短的
  [☆] 动态日程
      插件：15 分钟决策窗、可打断、挂起续做、质量闸
      我们：有今日日程 + 顺延（companion.ts 已实现）
      补法：补"挂起后回去接着做"，补"你叫她就放下手上的事"
  [☆] 情绪状态机
      插件：基线、衰减、冷静期、负面软化、道歉回温
      我们：情绪与反思，更像记录，不是状态
      补法：好感/心情两轴 + 冷静期（好感跌破阈值后一段时间不主动）
  [☆] 关系阶段
      插件：好感 + 认识天数 → 措辞与主动性变化
      我们：无
      补法：三档（生疏/熟悉/亲近），只影响称呼、频率、能否开玩笑
  [☆] 时间与环境
      插件：她所在城市/时区、天气、节日节气、穿搭
      我们：只有天气城市
      补法：加"她所在城市"（与用户城市分开）、节日与节气；
            穿搭作为人设的一部分，不做独立系统
  [☆] 未完成事项
      插件：最多 3 条、最多 4 天
      我们：无
      补法：与 3.2 的"未完话题"共用一份数据
  [○] 生理周期 / 梦 / 亲密场景
      桌宠场景不建议做，容易变成噪声与合规风险

3.4 整合与引导（对标 private_companion）
  [★] 引导里没有"选立绘"
      现在三步：称呼 / Key / 语音
      缺：导入立绘（用户第一眼看到的就是立绘，这一步不能少）
  [☆] 没有"今天她的状态"总览
      现在概览是状态数字，缺一张卡：心情、精力、陪了多久、下一次日程
  [☆] 设置页分组
      见上一份《设置页整合方案》，17 面板 → 6 组 10 页
  [○] 3D 小屋
      桌宠不需要，成本高、收益低

3.5 跨层契约（最大的差距）
  四个插件之间是互相读的：
    主动层开口前读记忆（按由头）+ 读身体与日程（决定该不该说）
    说完写回记忆（事件槽）
    日程与情绪作为"由头"的来源
  我们现在：记忆、主动、日程、情绪各是一个 IPC 模块，
            彼此不读对方的状态。
  结果：她"记得你"和"主动找你"是两件事，"她累了"和"她少说话"也是两件事。

  建议的最小契约（三个读、一个写）：
    读 memory：按当前由头取 3 条相关记忆
    读 body：精力 / 心情 / 社交能量（缺失时按中性值）
    读 agenda：当前这一段在做什么、下一段几点
    写 memory：主动消息发出后，写一条事件槽
  伪代码：
    const cue = pickCue({ unfinished, agenda, lastTalkAt })
    if (!cue) return                      // 派不出由头就不说
    if (!passGate({ quiet, cooldown, dailyCap, energy })) return
    const memories = memory.recall({ cue, slots: ['event','preference'], limit: 3 })
    const line = await generate({ cue, memories, body, agenda })
    if (!(await shouldSay(line))) return
    await send(line)
    memory.write({ slot: 'event', text: line, source: 'proactive', at: now })
    ledger.record({ cue, sentAt: now })

  这一段落地，三个插件的核心优势就同时有了。

4. 补齐顺序
============================================================
P0（先做，做完"陪伴感"才成立）
  1. 统一 Live2D 口径：README 改掉"已接运行时"；设置页与引导明说当前是预览/降级
  2. 主动加"由头"：先做未完话题、日程节点、隔久问候三类
  3. 主动加"闸门"：安静时段、每日上限、连续未回复降频
  4. 记忆衰减接入桌面壳（decay 已有）
  5. 主动消息写回记忆（事件槽）
  6. 处理"游戏日常"与需求文档的冲突：删入口或改文档

P1（用户会问"为什么她没有"）
  7. 记忆分槽 + 来源 + 固定
  8. 最小身体模型：精力 / 心情 / 陪伴时长，离线补算
  9. 状态影响开口：精力低就少说或不说
  10. 日程挂起续做 + "叫她就放下手上的事"
  11. 关系阶段三档（称呼、频率、玩笑尺度）
  12. 引导第二步改成"选一个立绘"，Key 放第三步

P2（锦上添花）
  13. 说话习惯画像（句长、口头禅、emoji）
  14. 节日与节气、她所在城市
  15. 未完成事项清单（3 条 / 4 天）
  16. 多句连发 / 气泡打字机
  17. 情绪冷静期与道歉回温

5. 不要照搬的部分
============================================================
109 项 / 137 项配置
  面板里全列出来，普通用户看一眼就关掉。
  四个插件自己也在 README 里写"第一次只动四项就够"。
  我们要学的是它们把配置分层，不是把配置搬过来。

多用户、群聊、关系排行榜、跨用户去重
  单人桌宠没有这些场景，做了只会增加状态复杂度。

亲密场景
  默认关闭也不建议做，与桌宠的产品定位不一致，且有合规风险。

embedding 记忆
  单人、本地、数据量小，关键词 + 摘要召回够用。
  上 embedding 会带来额外费用与首启延迟。

正在输入
  桌面端没有"对方正在输入"的语义，换成气泡打字机更自然。

6. 需要你拍板的三个选择
============================================================
Q1 桌宠要不要"身体"？
   要：她会有"今天有点累，少说两句"的表现，人味更足；代价是多一套状态要维护、要解释。
   不要：永远稳定在线，简单，但"她有自己的生活"这条线就断了。
   我的判断：要，但只做三个数（精力/心情/陪伴时长），不做生理周期。

Q2 主动要不要"由头"？
   要：开口有理由，用户能看见"她为什么现在说这句"；代价是要维护未完话题与日程数据。
   不要：继续定时生成，实现简单，但永远像播报。
   我的判断：要。这一条是"像人"和"像定时器"的分界线。

Q3 记忆要不要分槽？
   要：记得住重要的、忘得掉琐碎的；代价是设置页要多一层解释。
   不要：一条流，简单，但记忆会越来越像日志。
   我的判断：要，但设置页只给"记性好一点 / 忘性大一点"两档，不暴露槽位与公式。

7. 验收：五条能观察到的行为
============================================================
  □ 连续三天没回应，她停下来，不再主动发；我先开口后她恢复
  □ 23:00 之后她不再说话，手动"试一句"也被拦下并说明原因
  □ 我上周说"周五要交东西"，周五下午她来问结果
  □ 她说"今天有点累"的那天，主动次数明显变少
  □ 导入一个 Live2D 模型，界面明确告诉我现在是完整运行还是首帧预览

这五条都成立，说明记忆、身体、主动三层真的接上了。
只做到前四条、第五条含糊，说明立绘这条线还在"看起来能用"的阶段。

8. 与上一份文档的关系
============================================================
《设置页整合方案》解决"这些东西放在哪、叫什么、能不能调"。
这份文档解决"这些东西本身有没有、彼此通不通"。
顺序上先补能力（本文件 P0），再动页面结构；
不然会把还没接上的能力，摆进一个更漂亮的空壳里。
